# Launchpad database — decision log

Schema: [`launchpad.dbml`](launchpad.dbml) (paste into https://dbdiagram.io).
Stack: Laravel 13 + PostgreSQL. Each entry: what we chose, and why.

| # | Decision | Chosen | Why |
|---|----------|--------|-----|
| 1 | Primary keys | ULID `char(26)` everywhere (`HasUlids`, `foreignUlid`, `ulidMorphs`). Laravel internals (`jobs`, `failed_jobs`, `personal_access_tokens.id`) keep `bigint`. | One id inside and outside; safe to expose; not guessable; time-sortable; mobile app can mint ids offline. Human URLs still use `handle` / `slug`. |
| 2 | Fixed value sets | `varchar` + `CHECK` constraint, mapped to PHP backed enums. | DB rejects bad values, type-safe in PHP, easy migrations (swap the CHECK), readable in any SQL tool. Native PG enums are painful to change. |
| 3 | Roles & permissions | Single `users.role` column (`member` / `reviewer` / `admin`); rules in Laravel Policies. Founder is derived (has products). | Matches the requirement exactly (admin = reviewer + more). No extra tables, every rule lives in code in one place. |
| 4 | Taking a vote back | (Correction: the code also counts `flagged`, see spec §15.) Soft removal: `votes.removed_at`; re-vote clears it, bumps `toggle_count`, updates `voted_at`. Counts `removed_at IS NULL AND status IN (counted, flagged)`; a `voided` vote never counts (see 86 to 87 for flagging). | Keeps the vote/unvote trail for anti-cheat with one table and simple queries. |
| 5 | Uploaded images | Path column on the owner (`users.avatar_path`, `products.logo_path`, `product_screenshots.path`) on a Laravel disk (local → S3/R2). One `StoreImage` action resizes, strips EXIF/GPS, converts to WebP. | Explicit ownership, simple queries, no heavy media package. |
| 6 | Topics | Staff-managed fixed list (admins create / rename / reorder); founders pick up to 3. | Keeps per-topic leaderboards and follows meaningful — no "AI" / "ai" / "A.I." fragmentation, no tag spam. |
| 7 | Launch day boundary | UTC: every day runs 00:00–24:00 UTC. `launch_date` is a `date`; all timestamps `timestamptz` in UTC. Go-live, day freeze, and digests all key off UTC midnight. | Neutral, no daylight-saving edge cases, one shared "today" for ranking and freezing. Clients show local-time countdowns. |
| 8 | Adjustable business rules | `settings` table (`key` PK, `value jsonb`, `updated_by`, `updated_at`), edited by admins in staff tools, cached, every change audited. Keys are seeded + declared in a PHP enum (type, default, bounds); admins change values, never invent keys. | Staff can change limits like "2 launches per maker per day" without a developer or deploy. |
| 9 | Comment depth | One level of replies. `parent_id` must point at a top-level comment; replying to a reply attaches to the same parent and sets `reply_to_user_id` (@-mention + notify). | Readable on phones, one simple query, satisfies "replies to comments". |
| 10 | Account deletion | Anonymise in place (`users.deleted_at`): wipe personal data, delete logins/follows/prefs, void votes on unfrozen days, show comments as "[deleted]", take products down. Row and id stay. | App stores and privacy law require deletion; anonymising keeps frozen rankings, threads, the audit log and anti-cheat history intact with no FK cascades. |
| 11 | Changing email | Pending change: `users.pending_email` + `pending_email_expires_at`. Confirm link to the new address, cancel link to the old one; `email` switches only on confirm. Google link stays (matched by provider id). | Typos or a hijacked session can't lock the owner out; voters stay verified throughout. |
| 12 | Product links | `products.website_url` (required main link) + `product_links` table (`kind`: app_store / play_store / github / x / linkedin / docs / other, max 5). Website + extras editable after launch. | Matches "edit the links" (plural) after launch; queryable kinds give the mobile app proper store badges. |
| 13 | Edits between approval and launch | Locked except `launch_date`. To change anything else the founder withdraws to draft (launch day cleared) and resubmits. No revisions table. Post-launch edits (description + links) go live at once and are logged in `audit_logs` with before/after. | Closes the "approve then swap" loophole with no extra tables; the audit log still answers "what did it say before?" when something is reported. |
| 14 | Profile links | `user_links` table (`kind`, optional `label`, `url`, `position`, max 5), sharing the `link_kind` enum with `product_links`. `users.links` jsonb removed. | One pattern and one validation rule for all links; queryable. |
| 15 | Live "best first" ranking | Postgres only. Each vote updates `product_hourly_stats` in the same transaction; a scheduled job recomputes `products.hot_score` every minute for today's live products; today's page reads `ORDER BY hot_score DESC`. Vote *counts* still push instantly over WebSockets. | One source of truth, nothing to sync, a few hundred rows per minute. Order lagging ≤60s is fine; Redis can be added later if needed. |
| 16 | Follow feed | Built at read time — no feed table. One query over `user_follows` + `topic_follows` → live products, `ORDER BY launched_at DESC, id DESC`, keyset pagination, **not cached** (amended 2026-10-21, see 34: the first plan said "cached per user ~60s"). Index `products (status, launched_at, id)`. | Launches arrive once a day, volume is small; no fan-out jobs or unfollow cleanup. |
| 17 | Search engine | Postgres only (built, see 62 to 68): stored generated `search_vector` (name A > tagline B > description C, `simple` config after the shared `launchpad_fold` function: NFKC, `unaccent`, lower case) with a partial GIN index, + a partial `pg_trgm` GIN index on the generated folded `name_search` for typos. Queries are built per token from `plainto_tsquery` (the last token as a prefix), never from raw input; the score has a tier term so fuzzy matches rank after real ones; the trigram threshold is 0.5. Topic and maker names are not indexed. Topic filter + sort in the same SQL. | No extra service, never out of sync, milliseconds at this scale. Meilisearch or pgvector can be added later behind the same endpoint. |
| 18 | View tracking | Built (see 69 to 76). A view is **one per device per product per UTC day** (device = HMAC of the `lp_did` cookie or `X-Device-Id`; the earlier "per hour" was changed), counted by `POST /products/{id}/view`, not for the maker, staff or bots, with a per-IP cap of 25 devices per product per day. Redis dedupe (`SET NX`, one Lua script) → counters flushed every minute by `launchpad:flush-views` into `product_hourly_stats.views` (the arrival hour) + `product_referrers_daily` (a referrer host reduced to an allowlist key, 50 sources per product per day). No raw per-visit rows; export ships hourly/daily totals. | Tiny storage, no personal data kept, dashboards read pre-aggregated numbers. |
| 19 | Device signal for anti-cheat | `device_hash = HMAC(device_id)`. Web: HttpOnly `lp_did` cookie (random ULID, 2 years). Mobile: `X-Device-Id` install id. Stored next to `ip_hash`. No browser fingerprinting. | Simple, privacy-friendly, no third-party script; combined with IP, account age, vote-burst and coordination signals it catches most abuse. |
| 20 | Email reliability | Custom outbox `email_messages`: row written in the event's transaction, unique `idempotency_key`, worker with `FOR UPDATE SKIP LOCKED`, backoff 1m → 24h, prefs re-checked at send time (`suppressed`), staff can see / resend. | Survives hours of provider outage, never double-sends, never sends to opted-out members, and leaves a full history. |
| 21 | Product slug | `NOT NULL` + unique. The UI prefills it from the name and the founder can edit it; the server never generates it, only validates (format, 3-80 chars, unique, reserved words blocked) and returns 422 on a clash. Editable only while `draft` / `changes_requested`, with a UI warning under the field that changing it breaks existing links. No redirect table. Frozen from `pending` onward. | Every product always has a URL; link changes are a deliberate act; no hidden slug logic or redirects. |
| 22 | Reported content | Never auto-hidden. Content stays visible until a reviewer acts; the staff queue is ordered by open-report count, then summed reporter reliability (derived: share of the reporter's past reports upheld), then oldest. Unverified / suspended reporters are ignored. | One person or a group of fake accounts can't silence a comment or a competitor's launch; no threshold to game. |
| 23 | Security data retention | Built (2026-10-21). `launchpad:purge-retention` runs daily at 03:15 UTC (`withoutOverlapping(60)`, `onOneServer()`), values in `settings`: `auth_events` deleted after 180 days (`retention.auth_events_days`); `votes` IP/device hash + user agent nulled when the product's `launch_date` is more than 90 days before today UTC (`retention.vote_hashes_days`; the vote stays); `rank_snapshots` after 180 days (`retention.rank_snapshots_days`, decision 28); `audit_logs` rows kept forever (append-only trigger), but their `ip_hash` and `user_agent` (written by `Audit`, so not free of personal data) are set to NULL once the row is older than `retention.audit_network_days` (default **365**, integer 30 to 3650; decided and built 2026-10-21). That is a fourth table in the same command (`PurgeAuditNetwork`, same chunks and cap, oldest first, partial index `audit_logs_unpurged_network_index`). The append-only trigger gained one narrow exception (migration `2026_10_21_000003`): an UPDATE passes only if it sets both columns to NULL, changes nothing else, and the transaction set the transaction-local flag `launchpad.audit_purge = on`, which only the purge sets; any other UPDATE, DELETE and TRUNCATE still raise. The flag is not a privilege boundary (any SQL-capable role can set it); the production `REVOKE` advice in the README stays. Each table is purged in chunks of 2,000 rows, at most 100 chunks per run (a backlog continues the next night), each chunk its own short transaction, locking only the purged rows (`SKIP LOCKED`; never a user or product row). A corrupt stored window falls back to its default, never to 0. **`risk_signals` purge built (sub-project 8, see 91):** `PurgeRiskSignals` deletes unreviewed signals after `retention.risk_signals_days` (365) and reviewed ones after `retention.risk_signals_reviewed_days` (90) from the review (365 at most from detection); reviewed once-per-account kinds are kept. | Cheating is caught in days or weeks; keeping raw signals longer only enlarges what a leak could expose. Amended 2026-10-22: default raised to 180 days (owner decision; about 13M rows at top-500 every 10 minutes; the setting still goes 7 to 365). |
| 24 | Live updates transport | Laravel Reverb (self-hosted WebSockets) with Laravel broadcasting + Echo. Channels: private `user.{id}` (bell count), public `product.{id}` (vote count), public `today` (re-rank). Runs in Sail; same protocol for the future mobile app. | First-party, no third-party data sharing, matches "update without refreshing"; one extra process to run. |
| 25 | One Google identity per account | `social_accounts` is unique on `(user_id, provider)` as well as `(provider, provider_user_id)`; an email match never links a second Google `sub` to an account that already has one (`google_identity_mismatch`). | A recycled or reassigned address (lapsed domain, Workspace) with `email_verified=true` must not take over an account already bound to someone else's Google identity. |
| 26 | Freezing a day (late arrivals) | `daily_rankings` is insert-only (row triggers on UPDATE/DELETE and a statement trigger on TRUNCATE). `launchpad:freeze-day` runs every minute, locks the day's live products in id order without `SKIP LOCKED`, and APPENDS any live product that has no row yet after the day's last rank; a day is frozen only once it has been over for 60 s (UTC date of `now - 60 s`), within a 31-day look-back (`--from` widens it). | A frozen order must never move, yet a held launch released later, a restore or a lagging go-live must not stay unranked for ever. Appending keeps both promises; the 60 s margin covers a host clock that lags slightly behind the cast that was judged "still today". |
| 27 | Hot score settings are decimal strings | `ranking.decay_exponent` and `ranking.early_bonus` are stored as JSON strings (`"0.9"`, `"0.35"`), validated with an anchored regex, `numeric` and `between`; `Settings::decimal()` re-checks shape and range on every read and falls back to the default. | `settings.value` holds integers or strings only; a float would round-trip badly and accept `1e2`, signs or a trailing newline. A bad stored value must never reach the ranking maths. |
| 28 | Rank snapshots | `launchpad:snapshot-ranks` every 10 minutes writes `(product_id, captured_at, rank, score)` for the top 500 of today at the floored 10-minute mark, one short transaction, `ON CONFLICT DO NOTHING`; gaps are never back-filled. Up to ~72,000 rows a day, no personal data. **Retention (built 2026-10-21):** `retention.rank_snapshots_days`, default **180**, integer 7 to 365, purged by `captured_at` in the daily `launchpad:purge-retention` job, with index `rank_snapshots_captured_at_index` (the primary key leads with `product_id` and cannot serve it). The 30-day default is a provisional engineering choice (about 2 million rows at steady state), not a product decision: **how far back the founder dashboard looks is still undecided**, and the admin can raise the window up to 365 days when sub-project 7 decides. | Today's order cannot be rebuilt afterwards, so the history is written from the start; it feeds "where it ranked". Without a window the table would only grow; a short, adjustable default bounds it until the dashboard's lookback is known. Amended 2026-10-22: default raised to 180 days (owner decision; about 13M rows at top-500 every 10 minutes; the setting still goes 7 to 365). |
| 29 | Deleted member's votes: a queued job | `DeleteAccount` dispatches `VoidDeletedMemberVotes` after its commit; it voids the member's votes on unfrozen days (idempotent, unique per user, 3 tries, chunks of 100), and `launchpad:sweep-deleted-member-votes` re-dispatches it hourly if a dispatch or a job was lost. | Voiding needs other makers' product rows; taking them inside `DeleteAccount` (which holds the member's user row) inverts the lock order against `CastVote` and deadlocks. A lost job would leave counted votes of a deleted member in a frozen ranking, hence the sweep. |
| 30 | Public channels carry only visible data | `product.{id}` (`vote.count`) and `today` (`rank.updated`) are public. Payloads are ids and counts (rank, votes), no scores, names or voters, and are sent only for products that are publicly visible (live, launched, maker available). `rank.updated` is published inside the queued listener (`ShouldBroadcastNow`), one pending job per day. | Anyone who knows an id can listen, so a hidden product's count (or a voter) must not leak; ordering and replays stay under control. The frame is a hint: clients re-read the API for exact data. |
| 31 | Comment depth, delete and removal | Built (community phases A and B). One level of replies, enforced by action and by trigger `comments_reply_depth` (parent exists, top-level, same product; `product_id`, `user_id`, `parent_id` never change). `POST` accepts any comment id of the product as `parent_id`; a reply to a reply attaches to the top-level ancestor and `reply_to_user_id` is the author answered (null when that account is deleted). Author delete = `deleted_at` plus **wiped body**; staff removal = `removed_at`/`removed_by`/`removed_reason` with the body **kept** for staff, never public; rows are never hard-deleted. A removed or deleted top-level comment is listed as a body-less placeholder only while it still has visible replies; a removed or deleted reply disappears. A removed comment is "missing" (404) to its author; deleting an already deleted comment is an idempotent 200; an unchanged edit is a 200 before the window check. A deleted account's comments read as deleted at once (anti-join on `users.deleted_at`). | Replies keep their parent; a real erasure for the author; evidence stays for staff; the database, not only the action, promises "one level". |
| 32 | Comment counters | `products.comments_count` (comments neither removed nor deleted) and `comments.replies_count` (visible replies of a top-level comment) change only by relative `SET n = n + 1` / `n - 1`, in the same transaction as the comment write, **under the product row lock** (every comment action locks exactly one product row, so one lock serialises all comment writes of a product). Both have a `CHECK >= 0`. A deleted account's comments stay counted (and are masked on reads) until the deleted-member job corrects the counters, because `DeleteAccount` may not take other makers' product rows. | Counters cannot drift and need no reconciliation job; the cost is that a hot launch serialises its comment writes for a few statements each. |
| 33 | Follow privacy and rules | Follower and following **counts are public** (`COUNT(*)` on the indexed follow tables, nothing denormalised); the **lists are private** (`GET /me/follows/users`, `/topics` only; no follower list exists anywhere). Self-follow 403 `self_follow` (also on unfollow); a deleted member is the uniform 404; a suspended member cannot be newly followed (409 `member_unavailable`) but a follow can always be taken back; no cap (limiter `follow` 20/min + 200/h is the brake); PUT and DELETE are idempotent (200, `changed` false on a repeat). `DeleteAccount` deletes the member's follows in both directions and topic follows; `DeleteTopic` deletes the follows of an unused topic (a topic in use stays 409). | The client asks for follow and a feed, not social graphs; lists invite harassment. |
| 34 | Following feed: read time, never cached | Amends 16. A two-branch `UNION` built at read time: followed makers (a `LATERAL` per followed member over `products_maker_id_launched_at_id_index`) and products carrying a followed topic, both with `visible()`, an available maker, `launched_at IS NOT NULL`, `maker_id <> me` and the cursor predicate, merged and cut to `per_page + 1`, `launched_at desc, id desc`, then hydrated in order; reasons (one member reason first, at most 3 topic reasons) come from two queries over the page's ids. `meta.has_follows` tells the client to show "follow someone" instead of an empty list. `me/*` is `no-store, private`; there is no feed cache. | A follow or an unfollow must show at once; the query is index-driven, so the 60-second cache of the first plan bought nothing; a single `OR` could not be planned without a Sort. |
| 35 | Lock order for follows and reports | Global order extended: a member's product rows (id order); the active-admin set (id order); then comment rows (top-level parent first, then the reply), open report rows of one target (id order), topic rows, and last user rows. **Follows** take only user rows, `FOR SHARE`, the actor and the target in one statement in id order, and never a product row (`FollowTopic`: topic row `FOR SHARE` first, then the actor). `DeleteAccount` locks the member's follow rows first (`ORDER BY follower_id, followed_id FOR UPDATE`) so two members deleting each other cannot deadlock on `(a,b)` and `(b,a)`. **`CreateReport`** takes the product `FOR SHARE`, the comment `FOR SHARE`, reads (does not lock) report rows, and locks the **reporter's user row `FOR UPDATE` last**; it re-checks reportability on the locked rows. | Share locks cannot deadlock with each other and wait for a deleting writer; a fixed key order removes the cross-delete cycle; locking the reporter last never inverts the product-before-user rule. |
| 36 | Report cap is a brake, one open report per target | One OPEN report per reporter per target (partial unique `reports_open_unique`); the check order is target 404, own content 403, **existing open report (200, nothing new)**, earlier dismissed report (409 `already_reviewed`), cap (409 `report_limit`), insert in a savepoint (a unique violation is the existing report). `community.report_open_cap` (20, 1 to 200) counts the reporter's open reports; because `CreateReport` serialises one reporter's requests with the reporter-row lock, the cap is exact per member (the plan expected a soft overshoot and chose no lock; the build took the lock, which is cheap because it is last). It is still a brake, not a security boundary: closing reports frees slots and the `report` limiter (5/min + 30/h) bounds the rate. Reports never hide content. | An idempotent repeat must not turn into a 409 at the cap; a dismissed reporter cannot nag; nothing a group of reporters does can silence content. |
| 37 | `DeleteTopic` writes its audit row first | `DeleteTopic` calls `Audit::record` (which takes `FOR KEY SHARE` on the actor's user row) **before** it deletes the topic's `topic_follows` rows. | `DeleteAccount` holds a user row `FOR UPDATE` and then deletes that member's follow rows; deleting follow rows first and then waiting for the actor row could close a deadlock cycle. A user row always comes before follow rows. |
| 38 | Retention chunks pick rows in a materialized CTE | The four purge statements (`PurgeVoteHashes`, `PurgeAuthEvents`, `PurgeRankSnapshots`, `PurgeAuditNetwork`) now read `WITH picked AS MATERIALIZED (SELECT ... ORDER BY ... LIMIT n FOR UPDATE SKIP LOCKED) UPDATE/DELETE ... FROM/USING picked`. | With `WHERE id IN (subselect with LIMIT ... SKIP LOCKED)` the planner may turn the sub-select into a semi-join and re-run it, so a chunk could touch more than `LIMIT` rows. `MATERIALIZED` makes the chunk bound independent of the plan. |
| 39 | Staff report queue: ranking and its limits | `GET staff/reports` is one row per target with at least one eligible open report (reporter verified, not suspended, not deleted). Order: `open_reports` desc, `score` desc (rounded to 6 places so equal sums tie), oldest eligible open report asc, target id. At most 100 rows: the top 70 by that order plus the 30 **oldest** remaining targets, so a flood of high-count targets cannot starve a lone real report; `meta.total_targets` and `meta.truncated` say what is not shown; no cursor. Targets that are removed, deleted, taken down or hidden stay listed (staff must be able to close them); drafts are 404. The detail lists the oldest 200 open reports (`open_total` is the real number), the latest 50 closed ones, and marks each report with `reporter_eligible`. Refines 22. | The queue is meant to be drained, so a fixed list beats paging an order that moves; the oldest lane keeps patient reports from starving. |
| 40 | Reporter reliability and habitual false reporters | Derived, never stored: `(upheld + 1) / (decided + 2)` over the reporter's closed reports with `handled_by` set (`resolved` = upheld, `dismissed` = not). A system close (`handled_by` null: deleted by its author, erased with a deleted account, deleted reporter) counts for nothing either way. A reporter with at least 3 decided reports and reliability below 0.25 has weight 0: not in `score`, not in the `open_reports` ordering count (still in `reasons`, the detail, and closed by a resolve). Refines 22. | A ring of fake accounts cannot out-rank real reports by number, and a deletion by the author must not reward or punish the reporter. |
| 41 | Resolution is per target and needs an open report | One resolve closes every open report of the target together (`resolved` for `remove_comment`/`take_down`, `dismissed` for `dismiss`). The target changes only if at least one open report was locked; with none it answers 200 `closed: 0` and writes nothing, no audit row (removal without a report is not provided). A comment already removed or deleted, or a product already taken down, is left as it is and its reports close as `resolved`, with no second removal audit row. `take_down` is admin only (existing `TakeDownProduct` rules); `remove_comment` and `dismiss` are reviewer or admin. The actor's role is read from the database before the locks and again after the last lock. Answer order is 403, 404, 422. Audit: `comment.removed`, `report.resolved`, `report.dismissed`, plus the existing `product.taken_down`. A reporter whose report was dismissed gets 409 `already_reviewed` on a re-report. | A target is judged once, not once per reporter; staff cannot use the queue as a general delete button; a replay is harmless; a demoted or suspended reviewer waiting on a lock writes nothing. |
| 42 | Suspension semantics | Admin only; never oneself or an admin (403 `cannot_suspend`, so the last admin stays). `SuspendUser` locks the active-admin set (the actor must be in it), then the target row `FOR UPDATE`; no product row. It sets `suspended_at`/`suspended_reason`, runs `SignOutEverywhere` and audits `user.suspended`; idempotent (the first reason and time stay, no second audit row). Products, comments, votes and follows stay public and unchanged (content leaves through reports; votes are sub-project 8's call); open Reverb sockets are not closed (the next channel authorisation is refused). `RestoreUser` clears both columns, audits `user.restored` with `previous_reason`, and does not bring sessions back. | Reversible and cheap: no cascade over product rows, counters or ranking. |
| 43 | Deleted member's comments: a queued job and a sweep | `DeleteAccount` dispatches `DeleteMemberComments` after its commit (same pattern as 29). Unique per user (`$uniqueFor` 3600), `$timeout` 60, 3 tries, backoff 10 s then 60 s, 45 s budget per run after which the rest goes to a fresh job through the bus dispatcher. Per comment, its own transaction under the product row (then the top-level parent, the comment, its open reports): a counted comment is wiped and the counters corrected; a staff-removed comment only loses its body (`removed_*` stays, no counter change); the comment's open reports close as `resolved` by the system (`account_deleted`). At the end the member's own open reports close as `dismissed` by the system (`reporter_deleted`), only for targets with no other eligible open report. `launchpad:sweep-deleted-member-comments` runs at minute 30 (`30 * * * *`, lock 10 min) and re-dispatches for deleted members with unerased comments or closable reports; the schedule now has 7 events. Production needs an async queue and a running worker. | Erasing needs other makers' product rows, which `DeleteAccount` (holding the member's user row) must not take. Personal text must go; the removal record stays. |
| 44 | Privacy of report text and comment bodies | Reporter identity, `details` and staff notes are staff-only (detail and history); a member's response never shows other reporters or counts. Report rows are kept after closing, including a deleted reporter's `details` text (history); only comment bodies of a deleted member are erased (wiped, and the body of a staff-removed comment too). Audit `meta` holds ids, enum values and short staff-written reasons, never names, e-mails or bodies. | Staff need the history to judge reliability; a deleted member's own words must not stay readable. |
| 45 | Two stores: the bell and the outbox | Event-driven notifications are written by one action, `RecordNotification`, as TWO rows in one transaction: a bell row in `notifications` (always, for a live, non-suspended recipient, verified or not) and, when the type has a mail, an outbox row in `email_messages`. The idempotency keys are derived from the event, never from the clock: bell `review:{review_id}`, `product_live:{product_id}:{launch_date}`, `comment:{comment_id}`; mail `review_outcome:{review_id}:{maker}`, `product_live:{product}:{date}:{maker}`, `new_comment:{kind}:{product}:{yyyymmddHH of the comment's created_at}:{user}`. Both inserts are `ON CONFLICT DO NOTHING`, and the mail insert is attempted even when the bell row already existed (the repair rule). `User` uses `RoutesNotifications`, not `Notifiable`, and there are no Laravel `Notification` classes for new mail (the three auth mails keep their queued notifications). Refines 20. | A lost job, a retry and the reconcile sweep must write each row once; the bell must work for a member who cannot get mail; Laravel's polymorphic table would have been the wrong shape. |
| 46 | Preferences gate email only | A missing `email_preferences` row means on; only the six optional types can be stored (database CHECK from `EmailType::preferenceTypes()`), so verify, reset and email-change mail can never be switched off. The preference is read at enqueue time (to save a row) and again at **send time**, where an opted-out row becomes `suppressed` with `last_error = opted_out`, no attempt counted: turning a type off at 10:00 stops mail queued at 09:00. The bell is never gated. Unverified, suspended and deleted recipients are suppressed too. | The rule that counts is the one at the moment of sending. |
| 47 | Producers plus a reconcile sweep: two nets | Three queued listeners (`NotifyReviewOutcome`, `NotifyProductLive`, `NotifyNewComment`; method `notify`, 5 tries, backoff 10/60/300/900 s) fail their own job on error and retry. `launchpad:reconcile-notifications` (`45 * * * *`, lock 30) re-derives the last 48 hours from state (reviews by a ULID-floor primary-key range, products by `launched_at`, comments that still count) through the same `NotificationDrafts` and the same keys, so a normal run creates nothing and a lost job or outbox row is filled in. The `email_messages` retention window must stay at least 72 hours (`Reconcile::MIN_EMAIL_RETENTION_HOURS`), because a purged `sent` row frees its key. A reply goes to `reply_to_user_id`, else the top-level author; one row per person, kind `reply` wins; never the commenter. | A queue outage must delay a notification, not lose it; the mail key hour comes from the comment, so listener and sweep agree. |
| 48 | Outbox claim, lease and fencing | `ClaimDueEmails` picks up to 50 due rows `FOR UPDATE SKIP LOCKED` inside a `MATERIALIZED` CTE (the same chunk-bound lesson as 38), then in the same short transaction marks them `sending`, counts the attempt and sets a 10-minute lease in `next_attempt_at`; the transaction commits before any send.
